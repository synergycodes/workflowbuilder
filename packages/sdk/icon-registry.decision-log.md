### Title: Icons registered by the app instead of lazy-loaded one by one

### Proposed by: Jan Librowski

### Date: 19.11.2026

## Context

Up to 3.x every Phosphor icon was its own `React.lazy` chunk, generated by the private `apps/icons`
workspace. Any of the 1526 names worked without configuration, but:

- an icon was requested only after its first render, then faded in, so every new screen flickered;
- the SDK `dist` held 1526 icon chunks that every consuming app's build copied, and the map of lazy
  imports alone cost about 23 KB gzip in the main bundle;
- `WBIcon` was a closed union baked into the SDK build, so an app installing the SDK from npm could
  not add an icon of its own;
- the SDK and `@workflowbuilder/ui` also imported `@phosphor-icons/react` directly, a second source of
  the same glyphs.

Icon names stay strings because they are stored in data: `node.data.icon`, templates, select options,
diagrams saved by users. Bundling an icon at build time therefore needs the app to say which names
exist.

## Decision

- The app registers the icons its data names: `<WorkflowBuilder.Root icons={defineIcons({ ... })}>`.
  Only the imported icons are bundled, and they render synchronously.
- Glyph data is the Iconify format (`{ body, width, height }`). Apps install `@iconify-icons/ph` (or any
  `@iconify-icons/*` set) themselves and import one file per icon; the SDK does not re-export icons.
  `fromIconify` turns an Iconify JSON set, such as one built from a folder of SVGs, into an icon set.
- Names stay PascalCase (`PlayCircle`), so saved diagrams and templates need no migration.
- `Register` is augmented by the app to type names against what it registered. Without the
  augmentation any string type-checks, because the SDK's own code and apps that skip it must compile.
- The SDK registers the names its own data uses (status options, AI tool and model options, the global
  variables group): see `src/icon/built-in-icons.ts`. App icons override built-in icons of the same name.
- Icons fixed in code (editor header, menus, modals, form controls) are imports passed as
  `<Icon icon={...} />`. The renderer lives in `@workflowbuilder/ui`, so the component library uses the
  same data without depending on the SDK.
- An unregistered name renders a same-size empty placeholder and logs one warning per name.
- A plugin registers the icons its own node types and templates name with `registerIcons` in its
  initializer, and types them by extending `PluginIconNames`, which every plugin package can augment.
  The app does not list plugin icons, so removing a plugin needs no change in the app; the demo's
  stubs for missing plugins rely on that. App icons win over plugin icons, plugin icons over built-in ones.

## Rejected alternatives

- **Keeping every Phosphor name available by default** (one lazily loaded chunk with the whole set):
  still a flash on first use and about 180 KB gzip, for apps that name a few dozen icons.
- **Iconify's React component with its public API**: fetches icons from `api.iconify.design` at
  runtime, which breaks air-gapped deployments, and renders empty on the first render.
- **`unplugin-icons`**: compiles static imports only, so it cannot resolve names stored in data.
- **Semantic names for the editor's own icons** (`'close'`, `'expand'`) so apps can swap them: not
  needed yet, and it can be added later without breaking the imports.

## Follow-up

Names that only arrive at runtime, for example from a backend, have no loader yet. If an app needs one,
a `loadIcons` prop taking a loader the app supplies (its own icon set behind a dynamic import) adds it
without a breaking change. The SDK itself ships no icon set for apps. (follow-up: icon-runtime-loader)

## Status

Accepted. Supersedes the two "Lazy-loaded Icons" decision logs of `apps/icons`, removed with the workspace.
