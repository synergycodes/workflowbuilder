# Testing

The tested unit is the plugin. That is `WorkflowBuilderPlugin`, the three Activities it registers, and the workflow-side code that its `./workflow` entry point runs in Temporal's V8 sandbox. The three Activities are `executeNode`, `emitEvent` and `updateStatus`.

The reference backend and worker in `apps/` are sample consumers of the plugin. What a node executor does is consumer code. No test covers the full path from HTTP request to database write.

```bash
pnpm --filter @workflowbuilder/temporal test
pnpm --filter @workflowbuilder/temporal typecheck        # gates the contract check below
pnpm --filter @workflow-builder/execution-core test
```

No Docker, no Temporal cluster, no API key and no database. Two suites start a dev server binary: the replay suite and the error-boundary suite. `@temporalio/testing` downloads that binary into the system temp directory, and downloads it again when the cached copy is more than one day old. Both therefore need network access on a clean machine, and on every CI runner.

## Replay safety

**Deterministic sandbox code.** [`replay-audit.md`](../execution-core/replay-audit.md) gives a verdict for each reviewed source of non-determinism. It also lists the rules that new sandbox code must follow. [`graph-runner.replay-determinism.test.ts`](../execution-core/src/graph-runner.replay-determinism.test.ts) enforces this. It runs each graph shape several times against the same deterministic mocks, then compares the sequence of port calls. The sequences must be identical. The test needs no server and completes in milliseconds.

**A real run.** [`test/replay/replay.test.ts`](test/replay/replay.test.ts) runs every scenario in [`test/fixtures/replay-scenarios.ts`](test/fixtures/replay-scenarios.ts) on a real Temporal dev server. It uses Temporal's own bundler, a real `Worker`, and the plugin's three Activities. The store and the node executors are test fixtures. There is one scenario per path through the sandbox code: a parallel wave that completes, a node failing under the default `fail` policy, a branch left unwired so the run closes `incomplete`, and a cancel while an Activity is in flight. For each, the test checks how the run ended, which events every node emitted, and how the Workflow Execution closed. It counts the scheduled Activities of each type and expects one `executeNode` per node that ran, one `emitEvent` per emitted event, and one `updateStatus`. Then it runs the scenario again with the workflow cache off, so every workflow task replays from the first event instead of continuing from a cached state ([`test/replay/README.md`](test/replay/README.md) has the mechanism). That second run is compared on the activity counts, the `sequence` numbers of the store writes, the events each node emitted, and the terminal statuses. A side effect that reaches the command stream on replay moves one of those.

**The plugin's own sandbox modules.** [`replay-audit.md`](../execution-core/replay-audit.md) covers what `execution-core` puts in the bundle. Five modules from `src/workflow/` are bundled alongside it, and their module-level code is all constant: `profile-validation.ts` builds two frozen key `Set`s and reads `Object.keys`/`Object.entries` of a caller-supplied profile map, `node-activity-options.ts` constructs one `TextEncoder` and a byte cap, `activity-profiles.ts` freezes the two default profiles, and `run-workflow.ts` calls `proxyActivities` and `createRunWorkflow()` at import time. None reads a clock, a random source or the environment, and none iterates a collection whose order the input does not fix. `activities-interface.ts` and `core-contract.ts` are types only.

**A history recorded by older code.** The test replays every file in [`histories/`](test/replay/histories/) against the current code, one recording per scenario. It also fails when a scenario has no recording or a recording belongs to no scenario. This check fails when the current code would issue a command that a recorded run never made. A Workflow Execution can wait for days, so this check is what makes it safe to change the package between releases. [`test/replay/README.md`](test/replay/README.md) describes how to record a history, and what to do when this check fails. The correct response is different before and after the first release.

**Where the guarantee stops.** Replay does not run an Activity again if Temporal recorded its result. A retry does run it again. The plugin schedules one Activity per node, on a profile that allows two attempts by default, so a node executor must accept that it can run more than once. A consumer raises or lowers that per node type through `nodeActivityProfiles`. `emitEvent` and `updateStatus` run on a fixed profile that allows five attempts. The workflow assigns each event its own `sequence` number, so a store can make that write idempotent. The reference worker does this with `ON CONFLICT (execution_id, sequence) DO NOTHING`. No test covers that write.

## Limitations

- **No CI job tests against the newest `@temporalio/*`.** Every job installs the pinned versions. A regression in the SDK therefore appears when someone upgrades, not on a pull request.
- **Temporal's `patched()` is not called anywhere.** There are two documented responses to a change in the emitted command sequence. You can put the new behaviour behind `patched()`, or you can release a major version and drain the runs that are in flight first. Because no `patched()` call exists, draining is the response available today. See [`README.md`](README.md) § "Versioning and replay".

[`pr-check.yml`](../../.github/workflows/pr-check.yml) runs these in two jobs. The `temporal` job covers this package. The `execution` job covers `execution-core`, the reference apps and the shared `ai-config` and `temporal-connection` packages. Both jobs trigger only on pull requests into `main`, so they do not gate a `release/*` pull request. [`release-temporal.yml`](../../.github/workflows/release-temporal.yml) re-runs this package's lint, typecheck, test and build on the release tag, plus the `execution-core` suite that the bundled runner comes from, then `publint` and `arethetypeswrong`, before it publishes.
