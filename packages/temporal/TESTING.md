# Testing

The tested unit is the plugin. That is `WorkflowBuilderPlugin`, the three Activities it registers, the workflow-side code that its `./workflow` entry point runs in Temporal's V8 sandbox, and the `./client` entry, `TemporalWorkflowEngine` and `lazyClient`. The three Activities are `executeNode`, `emitEvent` and `updateStatus`.

The reference backend and worker in `apps/` are sample consumers of the plugin. What a node executor does is consumer code. No test covers the full path from HTTP request to database write.

```bash
pnpm --filter @workflowbuilder/temporal test
pnpm --filter @workflowbuilder/temporal typecheck        # gates the contract check below
pnpm --filter @workflow-builder/execution-core test
```

No Docker, no Temporal cluster, no API key and no database. Four suites start a dev server binary: replay, error-boundary, durable-pause and resolve-node. `@temporalio/testing` downloads that binary into the system temp directory, and downloads it again when the cached copy is more than one day old. They therefore need network access on a clean machine, and on every CI runner.

## Replay safety

**Deterministic sandbox code.** [`replay-audit.md`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/execution-core/replay-audit.md) gives a verdict for each reviewed source of non-determinism. It also lists the rules that new sandbox code must follow. [`graph-runner.replay-determinism.test.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/execution-core/src/graph-runner.replay-determinism.test.ts) enforces this. It runs each graph shape several times against the same deterministic mocks, then compares the sequence of port calls. The sequences must be identical. The test needs no server and completes in milliseconds.

**A real run.** [`test/replay/replay.test.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/temporal/test/replay/replay.test.ts) runs every scenario in [`test/fixtures/replay-scenarios.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/temporal/test/fixtures/replay-scenarios.ts) on a real Temporal dev server. It uses Temporal's own bundler, a real `Worker`, and the plugin's three Activities. The store and the node executors are test fixtures. There is one scenario per path through the sandbox code: a parallel wave that completes, a node failing under the default `fail` policy, a branch left unwired so the run closes `incomplete`, a cancel while an Activity is in flight, a node that parks the run and resumes on a `resolveNode` Update, and two nodes parked in one wave that take their verdicts one after the other. For each, the test checks how the run ended, which events every node emitted, and how the Workflow Execution closed. It counts the scheduled Activities of each type and expects one `executeNode` per node that ran, one `emitEvent` per emitted event, and one `updateStatus` per status write: `running` at the start and the terminal one, plus `waiting` and a second `running` for a parked run. Then it runs the scenario again with the workflow cache off, so every workflow task replays from the first event instead of continuing from a cached state ([`test/replay/README.md`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/temporal/test/replay/README.md) has the mechanism). That second run is compared on the activity counts, the `sequence` numbers of the store writes, the events each node emitted, and every status write. A side effect that reaches the command stream on replay moves one of those.

**The plugin's own sandbox modules.** `replay-audit.md` covers what `execution-core` puts in the bundle. Six runtime modules from `src/workflow/` are bundled alongside it, plus `src/constants.ts`, and their module-level code is all constant: `profile-validation.ts` builds a duration pattern, numeric caps and two key `Set`s, `node-activity-options.ts` constructs one `TextEncoder` and a byte cap, `activity-profiles.ts` freezes the two default profiles, `verdict-validation.ts` defines a literal table of rejection messages, `sequenced-event-emitter.ts` and `constants.ts` export functions and string constants, and `run-workflow.ts` calls `proxyActivities`, `defineUpdate` and `createRunWorkflow()` at import time. None reads a clock, a random source or the environment, and none iterates a collection whose order the input does not fix. `activities-interface.ts` is types only, `core-contract.ts` holds types and re-exports `runGraph` from `execution-core`, and `index.ts` only re-exports.

Each run also keeps per-run state for parked nodes, a `Map` of waits and a `Set` of known node ids, used for lookups and membership only. The `resolveNode` handler and its validator write nothing to history until an Update is accepted, and the wait is a `condition()` with no deadline, so neither adds a command. [`durable-pause.decision-log.md`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/temporal/src/workflow/durable-pause.decision-log.md) has the reasoning, and the replay README § "Reading the change" lists what does and does not move the command sequence.

**A history recorded by older code.** The test replays every file in [`histories/`](https://github.com/synergycodes/workflowbuilder/tree/main/packages/temporal/test/replay/histories) against the current code: one set per released version, holding each scenario that version already had, plus a `v0-` set recorded on code no release has shipped yet. It also fails when a scenario has no recording or a recording belongs to no scenario. This check fails when the current code would issue a command that a recorded run never made. A Workflow Execution can wait for days, so this check is what makes it safe to change the package between releases. The replay README describes how to record a history, and what to do when this check fails. A red released recording is a compatibility break. A red `v0-` recording is a design signal, since that code has not shipped.

**Where the guarantee stops.** Replay does not run an Activity again if Temporal recorded its result. A retry does run it again. The plugin schedules one Activity per node, on a profile that allows two attempts by default, so a node executor must accept that it can run more than once. A consumer raises or lowers that per node type through `nodeActivityProfiles`. `emitEvent` and `updateStatus` run on a fixed profile that allows five attempts. The workflow assigns each event its own `sequence` number, so a store can make that write idempotent. The reference worker does this with `ON CONFLICT (execution_id, sequence) DO NOTHING`. No test covers that write.

## Limitations

- **No CI job tests against the newest `@temporalio/*`.** Every job installs the pinned versions. A regression in the SDK therefore appears when someone upgrades, not on a pull request.
- **Only one `patched()` id exists.** `wb-running-status-at-start` (from 0.3.0), which `runGraph` reaches through `VersioningPort`. Any other change to the emitted command sequence on a path an older run took still needs its own `patched()` id, or a major release that drains the runs in flight first. See [`README.md`](https://github.com/synergycodes/workflowbuilder/blob/main/packages/temporal/README.md#versioning-and-replay) § "Versioning and replay".

[`pr-check.yml`](https://github.com/synergycodes/workflowbuilder/blob/main/.github/workflows/pr-check.yml) runs these in two jobs. The `temporal` job covers this package. The `execution` job covers `execution-core`, the reference apps and the shared `ai-config` and `temporal-connection` packages. Both run on pull requests into `main` and into `release`, so the release pull request is gated too. [`release-temporal.yml`](https://github.com/synergycodes/workflowbuilder/blob/main/.github/workflows/release-temporal.yml) re-runs this package's lint, typecheck, test and build on the release tag, plus the `execution-core` suite that the bundled runner comes from, then `publint` and `arethetypeswrong`, before it publishes.
