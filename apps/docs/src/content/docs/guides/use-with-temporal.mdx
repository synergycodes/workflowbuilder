With the [`@workflowbuilder/temporal`](https://www.npmjs.com/package/@workflowbuilder/temporal) plugin, a diagram drawn in the Workflow Builder editor runs as a durable [Temporal](https://temporal.io) Workflow Execution. A diagram is the workflow people draw in the editor: its nodes and edges, saved as JSON. Every diagram runs on the same Temporal Workflow, so a new diagram needs no new Temporal code. You redeploy your Worker, the Node.js process that runs that code, only when you add a node type or change what a node does.

To start from working code instead, the [ready example](#try-the-example) runs the whole setup on your machine.

## How Workflow Builder works with Temporal

Workflow Builder is an open-source framework for workflow orchestration in your product. Besides the editor SDK and the Temporal plugin that this guide uses, it includes a reference execution backend and AI Studio, a demo app that shows each run live on the canvas.

  src={architectureImg}
  alt="Arrows from left to right follow a run. Your React app, with the Workflow Builder editor and your Run button, sends the diagram to your backend, where your mapper turns it into a definition and the Workflow Builder TemporalWorkflowEngine starts a run on the Temporal Service. Temporal sends tasks to your Worker, where the Workflow Builder plugin (WorkflowBuilderPlugin) walks the graph and calls your executors, and the Worker returns results. Your store writes run events to your database, which can send them back to the canvas as optional run markers."

Three parts work together in a run.

**Workflow Builder** gives you two packages. The editor SDK (`@workflowbuilder/sdk`) runs in your React app, where people draw and configure the diagram. The Temporal plugin (`@workflowbuilder/temporal`) runs in your Worker. It walks the graph and runs each node the run reaches as its own `executeNode` Activity, Temporal's unit of work with its own timeout and retries, so a failed node is retried without re-running the rest. It follows the branch each branching node picks and reports every step to your store. The same package gives your backend a client, `TemporalWorkflowEngine`, which starts runs, cancels them and delivers decisions.

**Temporal** keeps the state of each run and records every step in Event History, so a run survives a crashed or restarted Worker. The Temporal Service hands tasks to your Worker and runs none of your code.

**Your code** connects the editor to the Workflow and holds the business logic. Your backend maps the diagram to a definition and starts the run. One executor per node type does that node's work, and a store writes run events to your database. Connection, credentials and deployment stay in your code, and the editor never talks to Temporal directly.

| On the canvas                      | On Temporal                                                                         |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| A diagram, each time it runs       | One Workflow Execution of `runWorkflow`, with Workflow Id `execution-<executionId>` |
| A node                             | One `executeNode` Activity                                                          |
| The node's label                   | The Activity's Summary in Event History                                             |
| The node's `type`                  | The executor that runs it in your Worker                                            |
| Values set in the properties panel | The node's `config`, passed to its executor                                         |
| A branching node's branch          | The `nextPort` its executor returns. Branches not taken are never scheduled         |
| The start node                     | `role: 'start'`, where the run begins                                               |

## Prerequisites

Before you start, set up the editor, a Node.js project for your backend and Worker, and a Temporal Service to run against.

- **Editor:** an app with the Workflow Builder SDK 4.x, see [Quick Start](/get-started/quick-start/wb-as-react-component/).
- **Node.js project:** TypeScript, Node.js 20.3+ and ESM (`"type": "module"`), for your backend and Worker. Keep it separate from the editor app, because the Worker runs in Node.js, not in the browser.
- **Temporal Service:** the [Temporal CLI](https://docs.temporal.io/cli/setup-cli) for local work, or any Temporal Service.

## Setup

Everything installs in your Node.js project with one command. The editor needs no new packages, only the Run button from [In the editor](#in-the-editor).

```bash
npm install @workflowbuilder/temporal @temporalio/worker @temporalio/activity @temporalio/client @temporalio/workflow @temporalio/plugin
```

The `@temporalio/*` packages are peers of the plugin and must all be one version, otherwise the Worker breaks at run time, not at install.

## In the editor

The editor is your app with the Workflow Builder SDK. Two things in it matter for a run: the node types people can drag onto the canvas, which the SDK calls the palette, and a way to start the run.

### Node types

The `type` you give a palette item is also the key of its executor in the Worker, so the editor and the Worker share one list of node types. Mark the item a run starts from with `isStartNode: true`, and the editor copies the flag onto the node when it is dropped. A branching node built on the `NodeType.DecisionNode` template generates one handle per branch, and its executor returns the handle of the branch the run takes. See [Add a custom node](/guides/add-a-custom-node/) for the rest of a palette item.

```ts
// editor: nodes/trigger.ts
import type { PaletteItem } from '@workflowbuilder/sdk';

import { defaultPropertiesData } from './default-properties-data';
import { type TriggerNodeSchema, schema } from './schema';
import { uischema } from './uischema';

export const trigger: PaletteItem<TriggerNodeSchema> = {
  type: 'trigger', // the executor key in the Worker
  isStartNode: true,
  icon: 'Lightning',
  label: 'Trigger',
  description: 'Starts the workflow',
  defaultPropertiesData,
  schema,
  uischema,
};
```

### Start a run

An [editor plugin](/guides/build-a-plugin/) adds a Run button to the editor header. It reads the diagram with [`getStoreDataForIntegration()`](/api/store/getstoredataforintegration/) and posts it to your backend.

```tsx
// editor: run-on-temporal.tsx
import {
  EditorHeaderControlsContent,
  getStoreDataForIntegration,
  registerComponentDecorator,
  showSnackbar,
} from '@workflowbuilder/sdk';

function RunButton() {
  async function run() {
    const { nodes, edges } = getStoreDataForIntegration();
    try {
      const response = await fetch('/api/runs', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ nodes, edges }),
      });
      if (!response.ok) {
        showSnackbar({ variant: 'error', title: 'Could not run the diagram', subtitle: await response.text() });
      }
    } catch {
      showSnackbar({ variant: 'error', title: 'Could not reach the backend' });
    }
  }

  return (
    <EditorHeaderControlsContent>
      <button type="button" title="Run the diagram on Temporal" onClick={() => void run()}>
        Run
      </button>
    </EditorHeaderControlsContent>
  );
}

export function runOnTemporal(): void {
  registerComponentDecorator('OptionalAppChildren', { content: RunButton, name: 'run-on-temporal' });
}
```

The `OptionalAppChildren` slot only mounts `RunButton`, and `EditorHeaderControlsContent` places the button in the editor header. Pass the plugin to the editor with `<WorkflowBuilder.Root plugins={[runOnTemporal]} />`.

A browser sends a CORS preflight before it posts JSON to another origin, and the backend in this guide does not answer it. Serve the editor and the backend from one origin instead, for example with a Vite proxy:

```ts
// editor: vite.config.ts
import react from '@vitejs/plugin-react';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [react()],
  server: { proxy: { '/api': 'http://127.0.0.1:3210' } },
});
```

## On your backend

Your backend receives the diagram from the editor, maps it to a definition the plugin can run and starts the run with `TemporalWorkflowEngine`, the plugin's client.

```ts
// server.ts
import { TemporalWorkflowEngine, lazyClient } from '@workflowbuilder/temporal/client';
import { randomUUID } from 'node:crypto';
import { createServer } from 'node:http';

import { toDefinition } from './to-definition';

const engine = new TemporalWorkflowEngine({
  client: lazyClient({ address: process.env.TEMPORAL_ADDRESS }),
});

createServer(async (request, response) => {
  if (request.method !== 'POST' || request.url !== '/api/runs') {
    response.writeHead(404).end();
    return;
  }
  // An error thrown in this async handler would stop the whole process.
  try {
    let body = '';
    for await (const chunk of request) body += chunk;

    const workflowId = 'my-diagram'; // the diagram's id, not the Temporal Workflow Id
    const executionId = randomUUID(); // one run
    await engine.submit({
      workflowId,
      executionId,
      definition: toDefinition(JSON.parse(body), workflowId),
      triggerPayload: {},
      variables: {},
      global: {},
    });
    response.writeHead(201, { 'Content-Type': 'application/json' }).end(JSON.stringify({ executionId }));
  } catch (error) {
    response.writeHead(400).end(error instanceof Error ? error.message : String(error));
  }
}).listen(3210);
```

The engine connects on its first call, not when your backend starts, so your backend can start before Temporal does. If the connection fails, that call throws and the next call tries again. `lazyClient` closes the connection of each failed attempt, which a factory built on `Connection.connect` would leave open. A single `catch` keeps the process up, and the example's [`bridge.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/worker/src/bridge.ts) also tells a bad diagram (400) from a Temporal error (502).

### Get the diagram

The Run button sends the diagram's nodes and edges in the request body. If your backend already saves diagrams (see [Persistence](/get-started/persistence/rest-api/)), it can load the diagram by `workflowId` instead.

### Describe your node types

The mapper and the Worker share one type with a variant per node type.

```ts
// nodes.ts
import type { BaseNode } from '@workflowbuilder/temporal';

type Branch = { label: string; sourceHandle: string };

type TriggerNode = BaseNode & { type: 'trigger'; config: Record<string, unknown> };
type ActionNode = BaseNode & { type: 'action'; config: { message: string } };
type DecisionNode = BaseNode & { type: 'decision'; config: { decisionBranches: Branch[] } };
export type MyNode = TriggerNode | ActionNode | DecisionNode;
```

### Map the diagram

The plugin does not read the editor's diagram format, so a mapper turns nodes and edges into a `WorkflowDefinition`, a plain graph of nodes and edges with nothing Temporal-specific in it. `type` must match an executor key, and `label` becomes the node's Summary in Event History. The graph has to meet these rules, or the run fails:

- Exactly one node has `role: 'start'`, and no edge leads into it.
- Every other node has at least one incoming edge. A node left unconnected on the canvas fails the run before any node executes.
- The graph has no loops. A run whose graph has one fails as stalled.

Check these rules in the mapper if the editor allows such diagrams. The example blocks edges into the start node in the editor with `isValidConnection`, see its [`app.tsx`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/editor/src/app.tsx).

| From the editor                                | To the definition                       |
| ---------------------------------------------- | --------------------------------------- |
| node `id`                                      | `id`                                    |
| `data.type`                                    | `type`, the executor key                |
| `data.properties` without `label` and `errors` | `config`                                |
| `data.properties.label`                        | `label`, the Summary in Event History   |
| `data.isStartNode`                             | `role: 'start'`                         |
| edge `source`, `target`                        | `sourceNodeId`, `targetNodeId`          |
| edge `sourceHandle`                            | `sourceHandle`, what `nextPort` matches |

```ts
// to-definition.ts
import type { WorkflowDefinition } from '@workflowbuilder/temporal';

import type { MyNode } from './nodes';

// The part of getStoreDataForIntegration() the mapper reads.
type Diagram = {
  nodes: { id: string; data: { type: string; isStartNode?: boolean; properties?: Record<string, unknown> } }[];
  edges: { id: string; source: string; target: string; sourceHandle?: string | null }[];
};

export function toDefinition(diagram: Diagram, workflowId: string): WorkflowDefinition<MyNode> {
  return {
    workflowId,
    nodes: diagram.nodes.map((node) => {
      const { label, ...config } = node.data.properties ?? {};
      delete config.errors; // the editor's form validation state, not configuration
      return {
        id: node.id,
        type: node.data.type,
        config,
        label,
        ...(node.data.isStartNode ? { role: 'start' } : {}),
      } as MyNode;
    }),
    edges: diagram.edges.map((edge) => ({
      id: edge.id,
      sourceNodeId: edge.source,
      targetNodeId: edge.target,
      sourceHandle: edge.sourceHandle ?? undefined,
    })),
  };
}
```

A complete version with validation is in the example's [`to-definition.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/worker/src/to-definition.ts).

### Start the run

`engine.submit` in [`server.ts`](#on-your-backend) starts the run. `workflowId` names your diagram, and a new `executionId` identifies each run of it. `triggerPayload` is the data the run starts with, and executors read it as `context.triggerPayload` (the example passes an amount and a customer name). `global` holds the global variables defined in the editor, and `variables` holds values your backend adds at start. All three are stored in Event History as they are, so keep secrets in the Worker's environment.

### Cancel a run and deliver a decision

The same engine stops a run and delivers a person's decision to a run that waits for one (see [Executors](#executors)).

```ts
await engine.cancel(executionId);

const { error } = await engine.resolveNode({
  executionId,
  nodeId: 'approval-1',
  resolution: { output: { approved: true }, nextPort: 'approved' },
});
```

`resolution` is what the waiting node would otherwise return itself: its `output` and, for a node with branches, the `nextPort` to follow. When the run refuses a decision, `resolveNode` returns `error` with a code instead of throwing. For example, `verdict_already_delivered` means the node was already decided and `node_not_waiting` means it is not waiting, so your backend can tell the person why.

## In your Worker

The Worker is the Node.js process that runs your Temporal code, and the Temporal plugin runs inside it. The plugin's Workflow walks the diagram, and its `executeNode` Activity calls your executor for each node. You give it the executors, a store and a `workflows.ts` module.

```ts
// worker.ts
import { NativeConnection, Worker } from '@temporalio/worker';
import { WorkflowBuilderPlugin } from '@workflowbuilder/temporal';
import { fileURLToPath } from 'node:url';

import type { MyNode } from './nodes';

const plugin = new WorkflowBuilderPlugin<MyNode>({
  executors: {
    trigger: (_node, context) => ({ output: context.triggerPayload }),
    action: (node) => ({ output: { message: node.config.message } }),
    decision: (node, context) => {
      // pickBranch is your branching logic, for example evaluating each branch's conditions.
      const branch = pickBranch(node.config.decisionBranches, context);
      return { output: { branch: branch.label }, nextPort: branch.sourceHandle };
    },
  },
  store: {
    async emitExecutionEvent(executionId, sequence, type, payload, nodeId) {
      /* insert a row */
    },
    async updateExecutionStatus(executionId, status, errorMessage, outcome) {
      /* update the run */
    },
  },
});

const worker = await Worker.create({
  connection: await NativeConnection.connect({ address: process.env.TEMPORAL_ADDRESS }),
  taskQueue: plugin.taskQueue,
  workflowsPath: fileURLToPath(new URL('workflows.ts', import.meta.url)),
  plugins: [plugin],
});

await worker.run();
```

### workflows.ts

The `workflowsPath` above points at a module that has to export the plugin's Workflow, and one line does it. The TypeScript SDK bundles Workflow code from a single `workflowsPath`. The plugin leaves that slot to you so your own Workflows can share the bundle.

```ts
// workflows.ts
export { runWorkflow } from '@workflowbuilder/temporal/workflow';
```

Keep the export named `runWorkflow`, because the client starts the Workflow by that name.

If you give some node types their own timeout and retry settings (`nodeActivityProfiles`), pass the same map to the plugin, next to `executors` and `store`, and build the Workflow from it in this file:

```ts
// workflows.ts
import { createRunWorkflow } from '@workflowbuilder/temporal/workflow';

import { nodeActivityProfiles } from './node-activity-profiles';

export const runWorkflow = createRunWorkflow({ nodeActivityProfiles });
```

The plugin only checks the map when the Worker starts. The Workflow is what applies it, because Temporal takes an Activity's timeout and retry policy from the Workflow that schedules it. A map given only to the plugin passes the deploy, and every node runs with the default profile: 2 attempts, each limited to 10 minutes. The [package README](https://www.npmjs.com/package/@workflowbuilder/temporal) shows the format of the map.

### Executors

An executor is a function that runs one node type, and it is the only place where you write what your nodes do. Executors are keyed by node `type` (see [Node types](#node-types)). Pass your node union to the plugin as its type parameter, and TypeScript refuses to compile until every node type has an executor.

Each executor returns `{ output }`. A branching node also returns `nextPort`, the `sourceHandle` of the edge the run follows. Take it from the node's config, where the editor keeps the handle id of each branch (in the example, `source:inner:review`), instead of hardcoding it. The example's [`evaluate-branches.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/worker/src/evaluate-branches.ts) shows one way to pick a branch.

If an executor throws, Temporal retries that node's Activity. By default a node gets 2 attempts, each limited to 10 minutes. Throw `PermanentNodeExecutionError` when another attempt cannot help, for example after a 404, and the node fails at once. `TransientNodeExecutionError` marks an error worth retrying, and an error of any other type is retried the same way.

An executor can also pause the run until a person decides. It returns `{ waiting: true }`, the run waits in Temporal without holding a Worker, and your backend delivers the decision with `engine.resolveNode` (see [Cancel a run and deliver a decision](#cancel-a-run-and-deliver-a-decision)). More in [Pausing a run for a human](https://www.npmjs.com/package/@workflowbuilder/temporal#pausing-a-run-for-a-human).

### Store

The store is where run events and statuses land, so your app can show them. Implement `emitExecutionEvent` and `updateExecutionStatus` against any database. The status becomes `running` as soon as a run starts, before its first node, so this is where you can record when the run started.

Both methods run in Activities, so a retried write can arrive twice. Make `(executionId, sequence)` unique, so a duplicate event is rejected. Keep the first terminal status a run reaches and ignore a `running` or `waiting` that arrives after it. Keep the `outcome` that arrives with `completed`, because it is the run's result.

## See the run on the canvas

Your store receives an event each time a node starts, completes, fails, is skipped or starts waiting for a decision. To show the run on the canvas, stream these events back to the editor and mark each node with a component decorator in the `OptionalNodeContent` slot. The editor SDK has no run view of its own. The example draws one status marker per node: it streams the events in [`bridge.ts`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/worker/src/bridge.ts) and draws the markers in [`node-markers.tsx`](https://github.com/synergycodes/workflowbuilder/blob/main/examples/workflow-builder-temporal/editor/src/execution/node-markers.tsx).

AI Studio has a fuller run view, with an execution log and a Decide button for waiting nodes. Its code is in [`apps/ai-studio/src/components/execution`](https://github.com/synergycodes/workflowbuilder/tree/main/apps/ai-studio/src/components/execution) and [`apps/ai-studio/src/components/human-decision`](https://github.com/synergycodes/workflowbuilder/tree/main/apps/ai-studio/src/components/human-decision), and the reference backend in [`apps/backend`](https://github.com/synergycodes/workflowbuilder/tree/main/apps/backend) streams the events to it. Both are reference code for local development, and the backend has no authentication.

### What you see in Temporal UI

Temporal UI shows how the diagram maps onto Temporal. Each run of the diagram is one Workflow Execution, and each node is an `executeNode` Activity with the node label as its Summary. The `emitEvent` and `updateStatus` Activities between them are the plugin writing to your store. The `core_patch` Marker near the start records that the run started on plugin code from 0.3.0 or later, so a Worker replays it on the same code path. A successful run is Completed, with one `executeNode` Activity per executed node. **Send email** shows attempt 2, because the example fails that node's first attempt on purpose (`simulateOutage` in its config) so you can see Temporal retry it.

## Production

Run against [Temporal Cloud](https://docs.temporal.io/cloud) or a [self-hosted Temporal Service](https://docs.temporal.io/self-hosted-guide). The Temporal plugin does not configure the connection. The address, TLS and API key go into `NativeConnection.connect` in your Worker and into `lazyClient` in your backend. A namespace other than `default` goes into `Worker.create` and into the second argument of `lazyClient`, `{ namespace }`.

Each executed node adds its `executeNode` Activity and two `emitEvent` Activities (node started, node completed or failed) to Event History, and a skipped node adds one `emitEvent`. The plugin does not use Continue-As-New, so size very large diagrams against Temporal's [Event History limits](https://docs.temporal.io/workflow-execution/limits).

Event History stores the inputs of every run, including `variables`, as plain data. To encrypt them, add a [Payload Codec](https://docs.temporal.io/production-deployment/data-encryption).
