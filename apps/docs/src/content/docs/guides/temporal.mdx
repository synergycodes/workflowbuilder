A diagram authored on the canvas becomes one Temporal Workflow Execution. Each node becomes an Activity, so retries, timeouts, cancellation and full Event History come from Temporal rather than from code you write. This guide builds that integration from an empty folder: a Temporal Worker running the [`@workflowbuilder/temporal`](https://github.com/synergycodes/workflowbuilder/tree/main/packages/temporal) plugin, then an editor whose Run button executes whatever is on the canvas.

## What you will build

Three folders, two processes and a local Temporal server:

- **`worker/`**, the Node side. A Temporal Worker running the `@workflowbuilder/temporal` plugin with one executor per node type, a store that prints every event to the terminal, an HTTP bridge the editor posts diagrams to and reads events back from, and a client script that runs a hand-written diagram once.
- **`editor/`**, the browser app. A Workflow Builder canvas with two palette items, Trigger and Action, and a Run button that posts whatever is on the canvas to the bridge and paints each node's status as the events stream in.
- **`shared/`**, the wire types both sides agree on: the snapshot the editor sends and the events the worker streams back.

A run travels from the editor to the bridge to Temporal, and the node events come back the same way over Server-Sent Events.

The split the plugin draws is worth holding on to, because it is what makes the rest predictable:

| The plugin owns                                      | You own                                                  |
| ---------------------------------------------------- | -------------------------------------------------------- |
| How a graph executes: traversal, waves, error policy | What each node does: one executor function per node type |
| Event ordering and sequence numbering                | Where events and statuses are persisted: the store port  |
| The activity contract and its default timeouts       | Connection, credentials, deployment                      |

## Requirements

- [Node.js](https://nodejs.org/) 20 or newer.
- The [Temporal CLI](https://docs.temporal.io/cli#install). On macOS, `brew install temporal`.
- Nothing else. No Docker, no database, no API keys.

The snippets were verified with `@workflowbuilder/sdk` 2.3.0 and the Temporal TypeScript SDK 1.24.0. The plugin accepts any `@temporalio/worker` from 1.23.0 on.

:::note
Working inside the Workflow Builder repository instead? `pnpm infra:up` starts a Temporal server on the same ports in Docker, and you can skip the CLI.
:::

### workflows.ts, the one line that matters

`worker/src/workflows.ts`

```ts
// Temporal compiles the workflow bundle from this one module, so a plugin cannot register a
// workflow on your behalf. Re-exporting it is how the bundle picks it up.
export { runWorkflow } from '@workflowbuilder/temporal/workflow';
```

That one line is required, and it is the piece most integrations trip over. The TypeScript SDK builds the workflow bundle from a single module, so a plugin cannot register a workflow on your behalf: setting `workflowsPath` itself would take that slot away from you. Re-exporting from your own workflows module is how the bundle picks it up. Temporal's own AI SDK plugin works the same way.

One rule governs this file. Import only from `@workflowbuilder/temporal/workflow`, never from the package root. Everything reachable from here is compiled into Temporal's V8 sandbox, where Node built-ins, the worker package and the client package do not exist.

### The node types

Your nodes are yours, and the plugin never looks inside them. Declare the union the worker knows how to run.

`worker/src/nodes.ts`

```ts
import type { BaseNode } from '@workflowbuilder/temporal';

// One variant per palette item in the editor. `config` is what the properties panel saved,
// minus the label, which the mapper lifts onto the node itself.
type SharedConfig = { description?: string; status?: string };

export type TriggerNode = BaseNode & { type: 'trigger'; config: SharedConfig };
export type ActionNode = BaseNode & {
  type: 'action';
  config: SharedConfig & { message?: string; simulateOutage?: boolean };
};

export type GuideNode = TriggerNode | ActionNode;

export const NODE_TYPES = ['trigger', 'action'] as const satisfies readonly GuideNode['type'][];

export function isNodeType(type: string): type is GuideNode['type'] {
  return (NODE_TYPES as readonly string[]).includes(type);
}
```

### The executors

One function per node type. This is where what your nodes actually do lives.

`worker/src/executors.ts`

```ts
import { Context } from '@temporalio/activity';
import { type NodeExecutorRegistry, TransientNodeExecutionError } from '@workflowbuilder/temporal';

import type { GuideNode } from './nodes';

export const executors: NodeExecutorRegistry<GuideNode> = {
  trigger: (_node, context) => ({ output: context.triggerPayload }),

  action: (node) => {
    // Executors run inside the plugin's executeNode Activity, so Temporal's activity context
    // is available. Failing the first attempt on purpose makes the retry visible in Event
    // History; the retry itself is Temporal's, not this code's.
    const { attempt } = Context.current().info;
    if (node.config.simulateOutage === true && attempt === 1) {
      throw new TransientNodeExecutionError(
        'mail_server_busy',
        'Simulated outage on the first attempt. Temporal retries this activity.',
      );
    }
    return { output: { delivered: true, attempt, message: node.config.message ?? '' } };
  },
};
```

Two things are worth pointing out. Executors run inside the plugin's `executeNode` Activity, so Temporal's activity context is available and the action can read which attempt it is on. And the registry is a mapped type over your node union, so a missing or misspelled node type is a type error rather than a run-time surprise.

The error classes say whether another attempt is worth making. `TransientNodeExecutionError` is for a timeout, a rate limit or a 5xx. `PermanentNodeExecutionError` is for a rejected key or a 400, and it stops the activity on its first attempt regardless of the retry policy. Anything else thrown retries as normal.

### The store

The plugin decides what is emitted and in what order. Where it lands is yours. The port is two methods.

`worker/src/store.ts`

```ts
import type { ExecutionStore } from '@workflowbuilder/temporal';

import type { RunEvent } from '../../shared/protocol';

type Listener = (event: RunEvent) => void;

export type RunStore = ExecutionStore & {
  subscribe(executionId: string, listener: Listener): () => void;
  history(executionId: string): RunEvent[];
};

// The plugin decides what is emitted and in which order; this is where it lands. Here: the
// terminal, plus anyone subscribed. A real application writes rows instead. The port is the same.
export function createRunStore(): RunStore {
  const histories = new Map<string, RunEvent[]>();
  const listeners = new Map<string, Set<Listener>>();

  function publish(executionId: string, event: RunEvent): void {
    const history = histories.get(executionId) ?? [];
    // Activities are at-least-once: a retried emit carries the same sequence, and keying on
    // (executionId, sequence) is how delivery stays idempotent.
    if (event.kind === 'event' && history.some((held) => held.kind === 'event' && held.sequence === event.sequence)) {
      return;
    }
    history.push(event);
    histories.set(executionId, history);
    for (const listener of listeners.get(executionId) ?? []) listener(event);
  }

  return {
    async emitExecutionEvent(executionId, sequence, type, payload, nodeId) {
      const where = nodeId ? ` (${nodeId})` : '';
      const what = payload === undefined ? '' : ` ${JSON.stringify(payload)}`;
      console.log(`[${executionId.slice(0, 8)}] #${String(sequence).padStart(2, ' ')} ${type}${where}${what}`);
      publish(executionId, { kind: 'event', sequence, type, nodeId, payload });
    },

    async updateExecutionStatus(executionId, status, errorMessage) {
      console.log(`[${executionId.slice(0, 8)}] status ${status}${errorMessage ? `: ${errorMessage}` : ''}`);
      publish(executionId, { kind: 'status', status, errorMessage });
    },

    subscribe(executionId, listener) {
      const set = listeners.get(executionId) ?? new Set<Listener>();
      set.add(listener);
      listeners.set(executionId, set);
      return () => {
        set.delete(listener);
      };
    },

    history(executionId) {
      return [...(histories.get(executionId) ?? [])];
    },
  };
}
```

Activities are at-least-once, so a retried emit arrives with the same sequence number. Keying on the execution and the sequence is what keeps delivery idempotent. Here events go to the terminal and to anyone subscribed; in your application they go to a database, and the port is the same.

The store's `RunEvent` type is shared with the editor.

`shared/protocol.ts`

```ts
// Shared with the editor through type-only imports, so nothing here reaches a bundle.

export type SnapshotNode = {
  id: string;
  data: {
    type: string;
    isStartNode?: boolean;
    properties?: Record<string, unknown>;
  };
};

export type SnapshotEdge = {
  id: string;
  source: string;
  target: string;
  sourceHandle?: string | null;
};

export type DiagramSnapshot = {
  nodes: SnapshotNode[];
  edges: SnapshotEdge[];
};

export type RunRequest = DiagramSnapshot & {
  triggerPayload?: Record<string, unknown>;
};

export type RunResponse = {
  executionId: string;
  temporalUiUrl: string;
};

export type RunEvent =
  | { kind: 'event'; sequence: number; type: string; nodeId?: string; payload?: unknown }
  | { kind: 'status'; status: string; errorMessage?: string };
```

### Wiring the plugin

`worker/src/worker.ts`

```ts
import { NativeConnection, Worker } from '@temporalio/worker';
import { WorkflowBuilderPlugin } from '@workflowbuilder/temporal';
import { fileURLToPath } from 'node:url';

import { TEMPORAL_ADDRESS, TEMPORAL_NAMESPACE } from './config';
import { executors } from './executors';
import { createRunStore } from './store';

const store = createRunStore();

// The plugin owns how a graph executes. What each node does (`executors`) and where events
// land (`store`) are yours, and that is the whole split.
const plugin = new WorkflowBuilderPlugin({ executors, store });

const worker = await Worker.create({
  connection: await NativeConnection.connect({ address: TEMPORAL_ADDRESS }),
  namespace: TEMPORAL_NAMESPACE,
  taskQueue: plugin.taskQueue,
  workflowsPath: fileURLToPath(new URL('workflows.ts', import.meta.url)),
  plugins: [plugin],
});

console.log(`worker polling task queue "${plugin.taskQueue}" on ${TEMPORAL_ADDRESS}`);
await worker.run();
```

`plugin.taskQueue` is read back rather than typed out, so the worker and the client cannot drift apart. It defaults to `workflow-execution`.

## 3. Run a diagram once

Before drawing anything, prove the worker with a definition written by hand. This is also the shape the editor will produce later.

`worker/src/client.ts`

```ts
import { Client, Connection, WorkflowFailedError } from '@temporalio/client';
import { type WorkflowDefinition, executionWorkflowId } from '@workflowbuilder/temporal';
import { TemporalWorkflowEngine } from '@workflowbuilder/temporal/client';
import { randomUUID } from 'node:crypto';

import { TEMPORAL_ADDRESS, TEMPORAL_NAMESPACE, WORKFLOW_ID, temporalUiUrl } from './config';
import type { GuideNode } from './nodes';

// The same three nodes the editor draws later, written out by hand so the worker can be
// proven before any canvas exists.
const definition: WorkflowDefinition<GuideNode> = {
  workflowId: WORKFLOW_ID,
  nodes: [
    { id: 'trigger-1', type: 'trigger', label: 'New request', role: 'start', config: {} },
    {
      id: 'action-1',
      type: 'action',
      label: 'Send email',
      config: { message: 'Thanks for reaching out!', simulateOutage: true },
    },
    { id: 'action-2', type: 'action', label: 'Notify the team', config: { message: 'A new request arrived' } },
  ],
  edges: [
    { id: 'edge-1', sourceNodeId: 'trigger-1', targetNodeId: 'action-1' },
    { id: 'edge-2', sourceNodeId: 'action-1', targetNodeId: 'action-2' },
  ],
};

const client = new Client({
  connection: await Connection.connect({ address: TEMPORAL_ADDRESS }),
  namespace: TEMPORAL_NAMESPACE,
});
const engine = new TemporalWorkflowEngine({ client });

const executionId = randomUUID();
await engine.submit({
  workflowId: WORKFLOW_ID,
  executionId,
  definition,
  triggerPayload: { customer: 'Ada' },
  variables: {},
  global: {},
});

console.log(`started ${executionWorkflowId(executionId)}`);
console.log(`watch it: ${temporalUiUrl(executionId)}`);

// The engine starts the run and returns at once. Waiting for the outcome is ordinary Temporal
// client code.
const handle = client.workflow.getHandle(executionWorkflowId(executionId));
try {
  await handle.result();
  console.log('run completed');
} catch (error) {
  if (!(error instanceof WorkflowFailedError)) throw error;
  const reason = error.cause instanceof Error ? error.cause.message : error.message;
  console.error(`run failed: ${reason}`);
  process.exitCode = 1;
} finally {
  await client.connection.close();
}
```

## 4. What Event History shows

Open the `watch it:` link. The whole run is one Workflow Execution, with a Workflow Id of `execution-` followed by the execution id you generated.

Each node is an Activity of type `executeNode`, scheduled with the node's authored label as its Temporal Summary, so the history lists `New request`, `Send email` and `Notify the team` instead of a column of identical rows. A node with no label simply gets no summary, and Temporal falls back to showing the activity type. Filling in the label belongs to whatever builds the workflow input, which in this guide is the mapper in step 5.

Interleaved with those are `emitEvent` and `updateStatus` activities. Those are your store port being called through Temporal, which is what makes event delivery survive a worker restart.

The retry deserves a closer look, because Event History does not record it the way people expect. There is no failed-activity event for the first attempt. Instead the `ActivityTaskStarted` event for `Send email` carries `attempt: 2`, and the failure that caused it is attached to that same event as `lastFailure`. Its message is the one the executor threw, its type is `TransientNodeExecutionError`, and the code `mail_server_busy` sits in the failure details together with the attempt it died on.

The policy that allowed it is the plugin's default node profile, visible on the scheduled event as a `startToCloseTimeout` of 600 seconds and `maximumAttempts` of 2. Ten minutes and two attempts is the default because a node may call a model. To give some node types their own, see [Going further](#going-further).

## 5. Run it from the canvas

Now the drawing. The editor posts the canvas to the worker, and the worker maps it into the same definition shape you wrote by hand.

### From snapshot to definition

The editor speaks React Flow. The plugin wants nodes of `{ id, type, config }` and edges of `{ sourceNodeId, targetNodeId }`. This file is the only glue, and the plugin knows nothing about React Flow.

`worker/src/to-definition.ts`

```ts
import type { WorkflowDefinition, WorkflowEdgeDefinition } from '@workflowbuilder/temporal';

import type { DiagramSnapshot, SnapshotEdge, SnapshotNode } from '../../shared/protocol';
import { type GuideNode, NODE_TYPES, isNodeType } from './nodes';

// The editor's snapshot is React Flow data; the plugin wants `{ id, type, config }` per node
// and `{ sourceNodeId, targetNodeId }` per edge. This is the only glue.
export function snapshotToDefinition(snapshot: DiagramSnapshot, workflowId: string): WorkflowDefinition<GuideNode> {
  // Which node starts the run. A diagram may carry an explicit `isStartNode` flag; a node
  // dropped from the palette does not, so the trigger type identifies it when none does.
  const flagged = snapshot.nodes.some((node) => node.data.isStartNode === true);
  const isStart = (node: SnapshotNode) => (flagged ? node.data.isStartNode === true : node.data.type === 'trigger');

  const nodes = snapshot.nodes.map((node) => toNode(node, isStart(node)));
  if (!nodes.some((node) => node.role === 'start')) {
    throw new Error('The diagram has no start node. Add a trigger node, or flag one node with isStartNode.');
  }

  return { workflowId, nodes, edges: snapshot.edges.map(toEdge) };
}

function toNode(node: SnapshotNode, isStart: boolean): GuideNode {
  const { type } = node.data;
  if (!isNodeType(type)) {
    throw new Error(`Unknown node type "${type}". This worker has executors for: ${NODE_TYPES.join(', ')}.`);
  }

  // `errors` and `customErrors` are the editor's validation state, not node configuration.
  const { label, errors, customErrors, ...config } = node.data.properties ?? {};
  return {
    id: node.id,
    type,
    config,
    ...(typeof label === 'string' && label.trim() !== '' ? { label: label.trim() } : {}),
    ...(isStart ? { role: 'start' as const } : {}),
  } as GuideNode;
}

function toEdge(edge: SnapshotEdge): WorkflowEdgeDefinition {
  return {
    id: edge.id,
    sourceNodeId: edge.source,
    targetNodeId: edge.target,
    ...(edge.sourceHandle ? { sourceHandle: edge.sourceHandle } : {}),
  };
}
```

The label is lifted out of `properties` onto the node itself, which is what later becomes the Summary in Event History. The editor's validation state, `errors` and `customErrors`, is dropped. Everything else in `properties` becomes `config`, which is what the executor reads.

:::note
Identifying the start node takes two rules because a node dropped from the palette carries no start flag in the published SDK. The diagram's flag wins when it is there, and the trigger type identifies the entry point when it is not.
:::

### The bridge

The editor never talks to Temporal. It posts a snapshot to the worker and reads events back, so the browser needs one origin and no Temporal client.

`worker/src/bridge.ts`

```ts
import type { WorkflowEnginePort } from '@workflowbuilder/temporal';
import { randomUUID } from 'node:crypto';
import { type IncomingMessage, type Server, type ServerResponse, createServer } from 'node:http';

import type { RunEvent, RunRequest, RunResponse } from '../../shared/protocol';
import { WORKFLOW_ID, temporalUiUrl } from './config';
import type { GuideNode } from './nodes';
import type { RunStore } from './store';
import { snapshotToDefinition } from './to-definition';

export type BridgeOptions = {
  engine: WorkflowEnginePort<GuideNode>;
  store: RunStore;
  port: number;
};

const EVENTS_PATH = /^\/api\/runs\/([^/]+)\/events$/;

export function startBridge({ engine, store, port }: BridgeOptions): Server {
  const server = createServer(async (request, response) => {
    const path = new URL(request.url ?? '/', 'http://localhost').pathname;
    try {
      if (request.method === 'POST' && path === '/api/runs') {
        await startRun(request, response, engine);
        return;
      }
      const events = EVENTS_PATH.exec(path);
      if (request.method === 'GET' && events) {
        streamEvents(response, store, events[1]);
        return;
      }
      sendJson(response, 404, { message: `No route for ${request.method} ${path}` });
    } catch (error) {
      sendJson(response, 400, { message: error instanceof Error ? error.message : String(error) });
    }
  });

  server.listen(port, '127.0.0.1', () => {
    console.log(`bridge listening on http://127.0.0.1:${port}`);
  });
  return server;
}

async function startRun(
  request: IncomingMessage,
  response: ServerResponse,
  engine: WorkflowEnginePort<GuideNode>,
): Promise<void> {
  const body = JSON.parse(await readBody(request)) as Partial<RunRequest>;
  if (!Array.isArray(body.nodes) || !Array.isArray(body.edges)) {
    throw new TypeError('The body must be a diagram snapshot: { nodes: [], edges: [], triggerPayload?: {} }.');
  }

  const executionId = randomUUID();
  await engine.submit({
    workflowId: WORKFLOW_ID,
    executionId,
    definition: snapshotToDefinition({ nodes: body.nodes, edges: body.edges }, WORKFLOW_ID),
    triggerPayload: body.triggerPayload ?? {},
    variables: {},
    global: {},
  });

  const payload: RunResponse = { executionId, temporalUiUrl: temporalUiUrl(executionId) };
  sendJson(response, 201, payload);
}

function streamEvents(response: ServerResponse, store: RunStore, executionId: string): void {
  response.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    Connection: 'keep-alive',
  });
  const send = (event: RunEvent) => response.write(`data: ${JSON.stringify(event)}\n\n`);

  // Replay first: the browser subscribes after the run has started, so the first events are
  // already in the store's history.
  for (const event of store.history(executionId)) send(event);
  const unsubscribe = store.subscribe(executionId, send);
  response.on('close', unsubscribe);
}

function readBody(request: IncomingMessage): Promise<string> {
  return new Promise((resolve, reject) => {
    let body = '';
    request.setEncoding('utf8');
    request.on('data', (chunk: string) => {
      body += chunk;
    });
    request.on('end', () => resolve(body));
    request.on('error', reject);
  });
}

function sendJson(response: ServerResponse, status: number, payload: unknown): void {
  response.writeHead(status, { 'Content-Type': 'application/json' });
  response.end(JSON.stringify(payload));
}
```

Replace `worker/src/worker.ts` with the version below. The engine is the same `TemporalWorkflowEngine` the client script used, built here from a factory so the client connection is opened on the first run rather than at startup.

`worker/src/worker.ts`

```ts
import { Client, Connection } from '@temporalio/client';
import { NativeConnection, Worker } from '@temporalio/worker';
import { WorkflowBuilderPlugin } from '@workflowbuilder/temporal';
import { TemporalWorkflowEngine } from '@workflowbuilder/temporal/client';
import { fileURLToPath } from 'node:url';

import { startBridge } from './bridge';
import { BRIDGE_PORT, TEMPORAL_ADDRESS, TEMPORAL_NAMESPACE } from './config';
import { executors } from './executors';
import { createRunStore } from './store';

const store = createRunStore();

// The plugin owns how a graph executes. What each node does (`executors`) and where events
// land (`store`) are yours, and that is the whole split.
const plugin = new WorkflowBuilderPlugin({ executors, store });

const worker = await Worker.create({
  connection: await NativeConnection.connect({ address: TEMPORAL_ADDRESS }),
  namespace: TEMPORAL_NAMESPACE,
  taskQueue: plugin.taskQueue,
  workflowsPath: fileURLToPath(new URL('workflows.ts', import.meta.url)),
  plugins: [plugin],
});

// The editor never talks to Temporal itself. It posts a canvas snapshot here and reads the
// store's events back, so the browser needs one origin and no Temporal client.
const engine = new TemporalWorkflowEngine({
  client: async () =>
    new Client({ connection: await Connection.connect({ address: TEMPORAL_ADDRESS }), namespace: TEMPORAL_NAMESPACE }),
});
const bridge = startBridge({ engine, store, port: BRIDGE_PORT });

console.log(`worker polling task queue "${plugin.taskQueue}" on ${TEMPORAL_ADDRESS}`);
```

### The run plugin

Everything the Run button needs is an SDK plugin: one store, one call, two decorators. See [Build a plugin](/guides/build-a-plugin/) for the pattern.

`editor/src/execution/run-store.ts`

```ts
import { create } from 'zustand';

import type { RunEvent } from '../../../shared/protocol';

export type NodeRunStatus = 'running' | 'completed' | 'failed' | 'skipped';
export type RunPhase = 'idle' | 'starting' | 'running' | 'completed' | 'incomplete' | 'failed' | 'cancelled' | 'error';

export type RunState = {
  phase: RunPhase;
  executionId?: string;
  temporalUiUrl?: string;
  message?: string;
  nodeStatuses: Record<string, NodeRunStatus>;
};

const IDLE: RunState = { phase: 'idle', nodeStatuses: {} };

export const useRunStore = create<RunState>(() => IDLE);

export function runStarting(): void {
  useRunStore.setState({ ...IDLE, phase: 'starting' }, true);
}

export function runStarted(executionId: string, temporalUiUrl: string): void {
  useRunStore.setState({ phase: 'running', executionId, temporalUiUrl });
}

export function runErrored(message: string): void {
  useRunStore.setState({ phase: 'error', message });
}

const TERMINAL_PHASES: ReadonlySet<string> = new Set(['completed', 'incomplete', 'failed', 'cancelled']);

const NODE_STATUS_BY_EVENT: Record<string, NodeRunStatus> = {
  node_started: 'running',
  node_completed: 'completed',
  node_failed: 'failed',
  node_skipped: 'skipped',
};

// A retried activity emits no event, so a node keeps spinning through its attempts. The
// terminal status is written after the terminal event, so ending on it loses nothing.
export function applyRunEvent(event: RunEvent): void {
  useRunStore.setState((state) => {
    if (event.kind === 'status') {
      return TERMINAL_PHASES.has(event.status) ? { phase: event.status as RunPhase, message: event.errorMessage } : {};
    }
    const status = NODE_STATUS_BY_EVENT[event.type];
    if (!status || !event.nodeId) return {};
    return { nodeStatuses: { ...state.nodeStatuses, [event.nodeId]: status } };
  });
}

export function isRunOver(phase: RunPhase): boolean {
  return TERMINAL_PHASES.has(phase) || phase === 'error';
}
```

`editor/src/execution/run.ts`

```ts
import { getStoreDataForIntegration } from '@workflowbuilder/sdk';

import type { RunEvent, RunRequest, RunResponse } from '../../../shared/protocol';
import { applyRunEvent, isRunOver, runErrored, runStarted, runStarting, useRunStore } from './run-store';

let stream: EventSource | undefined;

export async function runFromCanvas(): Promise<void> {
  stream?.close();
  runStarting();

  // Whatever is on the canvas right now, in the snapshot shape the bridge maps.
  const { nodes, edges } = getStoreDataForIntegration();
  const request: RunRequest = { nodes, edges, triggerPayload: { customer: 'Ada' } };

  let response: Response;
  try {
    response = await fetch('/api/runs', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(request),
    });
  } catch {
    runErrored('Could not reach the bridge. Is `npm start` running in the worker folder?');
    return;
  }

  if (!response.ok) {
    const { message } = (await response.json().catch(() => ({}))) as { message?: string };
    runErrored(message ?? `The bridge answered ${response.status}.`);
    return;
  }

  const { executionId, temporalUiUrl } = (await response.json()) as RunResponse;
  runStarted(executionId, temporalUiUrl);

  stream = new EventSource(`/api/runs/${executionId}/events`);
  stream.addEventListener('message', (message) => {
    applyRunEvent(JSON.parse(String(message.data)) as RunEvent);
    if (isRunOver(useRunStore.getState().phase)) stream?.close();
  });
  stream.addEventListener('error', () => {
    if (isRunOver(useRunStore.getState().phase)) return;
    runErrored('Lost the event stream. Is the worker still running?');
    stream?.close();
  });
}
```

### Draw it and run it

Still in `editor/`:

```bash
npm run dev
```

Open the printed URL. The canvas starts empty on a first visit. By default the editor saves the diagram to the browser's [local storage](/get-started/persistence/localstorage/), so on later visits the last drawing comes back, and so does a diagram another Workflow Builder app saved on the same origin. Delete those nodes first, or pass `integration` to `WorkflowBuilder.Root` to save somewhere else.

1. Open the **Nodes Library** in the top left, drag a **Trigger** and two **Action** nodes onto the canvas, and connect them in a line.
2. Select the first action, give it a message, and turn on **Simulate an outage on the first attempt**.
3. Click **Run on Temporal**.

Each node shows a spinner while its Activity runs, then a check. The first action spins through both attempts, because a retry emits no event of its own: the node stays in the state its last event put it in until the next one arrives. The **Temporal UI** link opens that run's history, where the drawing you just made is a column of Activities named after your nodes.

Change a message and run it again. Nothing is deployed in between, because the diagram is data.

## Going further

- **Per-node-type timeouts and retries.** Replace the re-export in `workflows.ts` with `createRunWorkflow` and a profiles map. Hand the same constant to the plugin as well: the two sides are not linked for you, and a map given only to the plugin leaves every node on the default.
- **Branching.** A decision node returns the handle it picked as `nextPort`, and the runner fires only the edge whose handle matches, marking the rest skipped. The [sample](https://github.com/synergycodes/workflowbuilder/tree/main/examples/workflow-builder-temporal) has a worked version with a condition editor on the canvas.
- **Pausing for a human.** Temporal parks a workflow for free while it waits for a Signal or an Update. The plugin's `runWorkflow` does not expose that yet, so today an executor waits inside its Activity until a verdict lands in your store, under a node profile whose timeout covers it. This guide does not build one.
- **Temporal Cloud.** Address, namespace, TLS and API keys go on the two connections you own, in `worker.ts` and `client.ts`. Nothing in the plugin changes.
- **A real store.** Swap the terminal for your database. Nothing else moves.
- **Versioning.** A workflow can sit in Event History for days, so the package promises that a patch or minor release still replays a history an older version recorded. Read that promise before upgrading in production.

## Troubleshooting

| Symptom                                                       | Cause                                                        | Fix                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------- |
| Bridge answers `Unknown node type "x"`                        | A palette type with no executor                              | Add it to the node union and the executor registry                |
| Bridge answers `The diagram has no start node`                | No trigger on the canvas                                     | Add a trigger node                                                |
| Run button reports it cannot reach the bridge                 | Worker not running, or the Vite proxy points somewhere else  | Start the worker; check the proxy port matches `BRIDGE_PORT`      |
| Worker logs a warning about a profile with no executor        | A profile keyed by a node type this worker does not register | Correct the key, or ignore it if another worker handles that type |
| A node spins and never settles                                | Retries emit no events                                       | Expected; watch attempts in Event History                         |
| Workflow tasks retry forever with nothing in your store       | Workflow code and worker disagree, usually an SDK mismatch   | Put every `@temporalio/*` package on one version line and restart |
| Nodes appear in Event History as identical `executeNode` rows | Nodes have no label                                          | Make sure the mapper lifts `label` out of the properties          |
